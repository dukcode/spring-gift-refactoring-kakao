# 테스트 전략 문서

## 1. 테스트의 목적

> 이번 미션에서 테스트는 무엇을 위해 존재하는가?

리팩터링의 안전망이다. 구조 변경(서비스 추출, 스타일 정리, 불필요 코드 제거) 전후로 **작동이 바뀌지 않았음을 증명**하는 것이 테스트의 핵심 역할이다.

### 원칙

- 테스트는 리팩터링보다 먼저 작성한다.
- 테스트가 통과하는 상태에서만 구조를 변경한다.
- 구조 변경 후 테스트가 깨지면, 작동이 바뀐 것이다 — 즉시 되돌린다.

## 2. 검증할 행위 목록

> 어떤 행위를 선택했는가? 기준은?

### 우선순위 판단 기준

| 순위 | 기준 | 설명 |
|------|------|------|
| 1 | 비즈니스 복잡도 | 여러 단계의 흐름 조율, 도메인 규칙, 트랜잭션 경계가 있는가 |
| 2 | 리팩터링 영향도 | 서비스 추출 시 가장 많은 로직이 이동하는 곳인가 |
| 3 | 데이터 정합성 | 여러 엔티티의 상태가 일관되게 변경되어야 하는가 |

### 우선순위 분류

#### 높음

| 기능 | 판단 근거 |
|------|-----------|
| 주문 생성 | 가장 복잡한 비즈니스 로직. 재고 차감 + 포인트 차감 + 주문 저장 + 카카오 알림까지 7단계 흐름. 현재 `@Transactional` 없이 컨트롤러에 존재하여 리팩터링 영향이 가장 크다. |
| 재고 자동 관리 | 주문과 밀접. `Option.subtractQuantity()`는 재고 부족 시 예외를 발생시키는 도메인 핵심 규칙. |
| 포인트 차감 | 주문과 밀접. `Member.deductPoint()`는 잔액 부족 시 예외를 발생시키는 도메인 규칙. |

#### 중간

| 기능 | 판단 근거 |
|------|-----------|
| 상품 등록 | 카테고리 연관 관계 설정 + 이름 검증(카카오 제한) 로직이 있어 단순 CRUD보다 복잡. |
| 옵션 관리 | 중복 이름 체크, 마지막 옵션 삭제 방지 등 비즈니스 규칙 존재. |
| 위시리스트 | 중복 추가 방지(멱등), 소유권 검증 등 규칙 존재. |
| 회원가입/로그인 | 이메일 중복 체크, 비밀번호 검증 로직. |

#### 낮음 (리팩터링 안전망으로는 불필요)

| 기능 | 판단 근거 | 제외 사유 |
|------|-----------|-----------|
| 카테고리 목록 조회 | `findAll()` 위임 | 비즈니스 로직 없음 |
| 상품 목록 조회 | `findAll(pageable)` 위임 | 비즈니스 로직 없음 |
| 주문 목록 조회 | `findByMemberId(pageable)` 위임 | 비즈니스 로직 없음 |

## 3. 테스트 데이터 전략

> 어떻게 준비하고 정리하는가?

### 테스트 환경

- `@SpringBootTest(webEnvironment = RANDOM_PORT)` + RestAssured로 실제 HTTP 요청을 통한 통합 테스트
- RestAssured는 별도 스레드에서 서버를 구동하므로 `@Transactional` 롤백 불가
- 데이터의 생성과 정리를 `@Sql`로 처리

### 파일 구조

```
src/test/resources/sql/
├── common-init.sql                      # 공통 초기화 (전 테스트 공유)
├── order/
│   ├── success.sql                      # 정상 주문 (충분한 재고, 충분한 포인트)
│   ├── insufficient-stock.sql           # 재고 부족
│   ├── insufficient-point.sql           # 포인트 부족
│   └── zero-stock.sql                   # 재고 0
├── product/
│   ├── success.sql                      # 정상 등록 데이터
│   └── invalid-category.sql             # 존재하지 않는 카테고리
├── option/
│   ├── success.sql                      # 정상 옵션 데이터
│   └── duplicate-name.sql              # 중복 이름 시나리오
└── wish/
    ├── success.sql                      # 정상 위시 데이터
    └── duplicate.sql                    # 중복 추가 시나리오
```

### 적용 방식

```java
@Sql({"/sql/common-init.sql", "/sql/order/success.sql"})
@Test
void 주문_생성_성공() { ... }
```

## 4. 검증 전략

> 무엇을 어떻게 검증하는가?

### 검증 방식

행동 기반 테스트(Behavioral Test)로 진행한다.

- **시스템 경계(API)에서** — REST API 엔드포인트를 통해 테스트
- **사용자 시나리오를** — 사용자가 실제로 수행하는 행동 단위
- **최종 상태 기준으로** — 요청 처리 후의 결과 상태를 검증
- **검증한다** — external behavior만 검증 대상

### 검증 대상

| 검증 항목 | 도구 | 예시 |
|-----------|------|------|
| HTTP 응답 코드 | RestAssured | `.statusCode(201)` |
| 응답 본문 | RestAssured | `.body("id", notNullValue())` |
| DB 상태 | Repository/JdbcTemplate | 재고 수량, 포인트 잔액 확인 |
| 실패 시 미변경 | Repository | 예외 발생 후 원래 상태 유지 확인 |

### 기능별 검증 항목

#### 주문 생성 + 재고 + 포인트 (우선순위: 높음)

| 시나리오 | HTTP | 재고 | 포인트 |
|----------|------|------|--------|
| 정상 주문 | 201 | 차감됨 | 차감됨 |
| 재고 부족 | 에러 | 유지 | 유지 |
| 포인트 부족 | 에러 | 유지 | 유지 |
| 재고 0 | 에러 | 0 유지 | 유지 |

#### 상품 등록 (우선순위: 중간)

| 시나리오 | HTTP | DB |
|----------|------|----|
| 정상 등록 | 201 | 저장됨, 카테고리 연관 |
| 존재하지 않는 카테고리 | 404 | 변경 없음 |
| 카카오 이름 포함 | 400 | 변경 없음 |

#### 옵션 관리 (우선순위: 중간)

| 시나리오 | HTTP | DB |
|----------|------|----|
| 정상 추가 | 201 | 저장됨 |
| 중복 이름 | 400 | 변경 없음 |
| 마지막 옵션 삭제 | 400 | 유지 |
